# 89. UNIVERSAL POS PRINCIPLE

The ecosystem must contain ONE universal POS engine.

The POS must support:

- clothing
- fashion
- accessories
- shoes
- mobile
- laptop
- electronics
- pharmacy
- grocery
- restaurant
- cafe
- cosmetics
- general retail

Do NOT create separate POS engines for each business type.

Correct:

    Universal POS Engine

    Business Configuration
            ↓
    Required / Optional Fields
            ↓
    Business-Specific UI

    Clothing POS
    Electronics POS
    Pharmacy POS
    Restaurant POS
    Grocery POS

Business templates only modify configuration and presentation.

The core transaction, inventory, payment, audit, sync and reporting
architecture remains shared.

# 165. OFFLINE POS

POS must work offline where local data is available.

Offline sale:

    validate locally
    create local transaction
    create inventory event
    create payment event
    create audit
    create sync event
    commit

Later:

    sync with peers

Do NOT wait for internet to complete an otherwise locally valid sale.


# 166. OFFLINE INVENTORY

Offline inventory is based on the device's locally known ledger state.

When reconnecting:

    exchange events
    apply missing events
    rebuild/reconcile projection

Never discard an offline sale because another device changed the stock.


# 167. MULTI-DEVICE INVENTORY EXAMPLE

Initial:

    Stock = 10

Device A offline:

    Sale X = -2

Device B offline:

    Sale Y = -3

Reconnect.

Both events must survive.

Final:

    10 - 2 - 3 = 5

Do NOT use:

    "last device wins"

Do NOT overwrite one sale with another.


# 168. SYNCED PAYMENT EXAMPLE

Device A offline:

    Cash Sale = 1000

Device B offline:

    Bank Sale = 2000

Reconnect.

Both payments survive.

Wallet result:

    CASH +1000
    BANK +2000

No payment is overwritten.

    Fully Synced
    Partially Synced
    Local Only
    Sync Pending
    Conflict

This avoids misleading users.


# 174. DATA INTEGRITY CHECKS

System should be able to detect:

    inventory projection mismatch
    wallet projection mismatch
    missing event
    duplicate event
    broken reference
    invalid payment allocation
    invalid return quantity
    impossible balance
    orphan record
    corrupt backup reference

Detection must produce a visible diagnostic/audit result.

Never silently repair financial history.


# 175. REBUILDABLE PROJECTIONS

Rebuild commands may include:

    rebuildInventoryProjection
    rebuildWalletProjection
    rebuildReportIndexes
    rebuildRecordingIndex
    rebuildSearchIndex

Rebuild must derive from authoritative records.

The command must be safe to retry.


# 176. POS DELETE RULE

Do not expose a generic:

    DELETE SALE

button for completed financial records.

Instead expose appropriate actions:

    Cancel
    Void
    Return
    Reverse
    Correct
    Replacement

depending on state and permissions.


# 177. TRANSACTION STATE

Transactions may use states such as:

    DRAFT
    PENDING
    COMPLETED
    CANCELLED
    VOIDED
    PARTIALLY_RETURNED
    FULLY_RETURNED
    CONFLICT
    FAILED

State transitions must be controlled by the domain.

Do not allow arbitrary UI state mutation.


# 178. SALE STATE RULE

Example:

    DRAFT
       ↓
    CONFIRMED
       ↓
    PARTIALLY_RETURNED
       ↓
    FULLY_RETURNED

A completed transaction cannot simply jump to an arbitrary state.


# 179. RETURN STATE

Possible:

    DRAFT
    CONFIRMED
    REFUNDED
    PARTIALLY_REFUNDED
    CANCELLED

The domain must prevent:

    double refund
    double inventory return
    duplicate return event


# 180. PAYMENT STATE

Possible:

    PENDING
    COMPLETED
    FAILED
    REVERSED
    VOIDED

Do not mark a failed payment as completed merely because the UI
received a temporary success-like response.

    pos.discount.apply = true

    pos.expense.create = true
    pos.expense.max_amount = 5000

UI-only enforcement is insufficient.


# 184. USER/DEVICE SNAPSHOT IN REPORTS

Reports should optionally show:

    User
    Device

This is especially important in a multi-device ecosystem.

Do not interpret device as branch.

Device is simply the originating/trusted peer.


# 185. DEVICE FILTER

POS reports may filter by:

    device_id

Example:

    Sales from Android Device
    Sales from Windows PC

This is NOT branch reporting.

It is device-origin reporting.


# 186. DATA OWNERSHIP

Business data belongs to the ecosystem.

A device is a peer holding local state.

No device should be treated as a permanent "master branch".

Synchronization must allow multiple devices to create valid events.


# 187. EVENT ORDER

Do not assume:

    device timestamp = global event order

Use:

    event ID
    logical version where appropriate
    causal metadata where needed
    event relationships

Wall-clock timestamp is descriptive, not the sole conflict authority.


# 188. CONFLICT PRINCIPLE

Financial/inventory events:

    NEVER last-write-wins

Independent valid events:

    preserve both

Actual conflicting corrections:

    detect
    preserve source events
    create conflict record
    require controlled resolution

Never destroy one side merely to make the UI clean.


# 189. CONFLICT RECORD

sync_conflicts should contain enough information to understand:

    conflict_id
    event_id
    aggregate_id
    device_id
    conflict_type
    detected_at
    local_state_summary
    incoming_state_summary
    resolution_state
    resolved_by
    resolved_at
    resolution_action

Never silently discard the incoming event.


# 190. REPORT RECONCILIATION

    ↓
