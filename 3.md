# 199. LOCAL NETWORK P2P

When devices are on the same LAN:

    Device A
       ↓
    Local Discovery
       ↓
    Device B
       ↓
    Authentication
       ↓
    Direct Connection

Do not route large files through cloud when direct LAN P2P is
available.

# 200. INTERNET P2P

    Device A
       ↓
    Internet
       ↓
    Signaling / Rendezvous
       ↓
    WebRTC Negotiation
       ↓
    Direct P2P Attempt
       ↓
    TURN fallback if required
       ↓
    Device B

Signaling is for coordination.

Signaling is NOT the large-data transport.

# 213. FILE TRANSFER PROTOCOL

    START
      ↓
    META
      ↓
    CHUNK
      ↓
    ACK
      ↓
    VERIFY
      ↓
    COMPLETE

    file_id
    name

    size
    SHA-256
    chunk_size
    total_chunks


# 214. FILE TRANSFER START

Sender sends:

    file_id
    filename
    MIME type
    total size
    SHA-256
    chunk size
    total chunks

Receiver validates:

    permission
    available storage
    file size
    supported type
    transfer policy

Then accepts or rejects.


# 215. FILE CHUNKS

Never send:

    entire 2 GB file

as one memory object.

Instead:

    chunk 1
    chunk 2
    chunk 3
    ...
    chunk N

Chunk size must be configurable and bounded.

---

# 216. FILE ACKNOWLEDGEMENT

Receiver acknowledges durable chunks.

Sender tracks:

    sent
    acknowledged
    pending
    failed

A network failure must not necessarily restart the whole transfer.


# 217. FILE RESUME

Example:

    File = 1 GB

    Transferred = 650 MB

    Connection lost

Reconnect:

    resume from confirmed position

Do not restart from zero unless required.


# 218. FILE INTEGRITY

At completion:

    calculate SHA-256
      ↓
    compare sender hash
      ↓
    match?
       YES → COMPLETE
       NO  → CORRUPTED / RETRY

Never mark a corrupted transfer as complete.


# 219. PARTIAL FILES

Incomplete files must remain in controlled temporary storage.

Example:

    /temp/transfers/<file_id>.partial

After completion:

    verify
      ↓
    atomic rename
      ↓
    final location

Failed/cancelled temporary files must eventually be cleaned.


# 220. FILE CANCEL

Cancel must:

    stop sender
    stop receiver
    release handles
    remove incomplete temp state where appropriate
    preserve audit/transfer status

Cancellation must not corrupt unrelated files.


# 221. FILE RETRY

Retry transient errors.

Examples:

    temporary disconnect
    network timeout
    peer unavailable

Do not retry forever.

Use bounded exponential backoff.

Non-retryable errors:

    permission denied
    invalid metadata
    unsupported schema
    corrupted request
    insufficient storage

must become visible failures.


# 222. DUPLICATE FILE

If receiver already has:

    SHA-256 = ABC123

and sender wants to transfer same binary:

    transfer = 0 bytes

Reuse existing file.

If filename differs but content hash matches, the same content may be
referenced by multiple metadata records without duplicating binary data.


# 223. STORAGE FULL DURING TRANSFER

If storage becomes insufficient:

    pause/fail safely
    preserve transfer state
    show storage error
    do not corrupt completed data

Clean only safe temporary data.

Never delete user data automatically to make room unless explicitly
authorized by a configured cleanup policy.

# 246. UNKNOWN EVENT SCHEMA

    do NOT silently discard

    preserve raw event safely
    mark unsupported/quarantined
    report compatibility problem
    do not advance applicable cursor past unsafe data

# 247. SCHEMA VERSION
